대조했다. 실제 개발 대상은 IsaacLab 본체가 아니라 이 MuJoCo ROV 저장소다.
기존 변경 50개 파일을 먼저 `b7c49ec`로 커밋하고 개인 저장소의 `main` 및

## 수정한 결함

1. **수집 준비 표시와 시작 서비스의 시계 검사 불일치**: 준비 상태·서비스·정책
   관측·샘플 저장에 동일한 시계 조건을 적용했다. 시계 정지/역행 이후 이전 FCU
   무장·모드 캐시도 무효화한다. [회귀 증거](../contracts/PRE_VLA_COLLECTOR_READINESS_20260914.md).
2. **낮은 원본 카메라 주기로 수집 준비 가능**: 알려진 10 Hz 미만 또는 출력이
   꺼진 실행은 준비를 거절한다. 저장한 선택과 실제 실행 명령을 구분하고,
   `--ros2-image-hz` 등의 명시적 실행 인자를 provenance에 반영한다.
3. **세션 도중 센서·물리 설정 변경**: 준비 시점부터 세션 종료까지 설정을 잠근다.
   시연 저장 후 대기 중에도 잠금은 유지한다. 실패한 레코더가 종료됐다면 세션을
   닫아 잠금을 복구할 수 있다. 열린 창 닫기는 녹화 종료가 아니다.
4. **표시 속도와 센서 출력 혼동**: `ROS 센서 출력`, `광학`, `미리보기 속도`로
   나눴다. 브라우저는 최신 프레임만 0/2/4/10 fps로 요청하고 중복 요청과
   숨겨진 탭의 요청을 제한한다. 녹화는 원본 ROS 토픽에서 계속 진행한다.
5. **고정 거리 광학 근사**: 경량 광학에서 실제 같은 장면의 RGB·깊이를 함께
   렌더한다. 축 방향 깊이를 픽셀별 광선 거리로 바꾸고, 수면 아래 구간만
   색 감쇠·산란에 사용한다. 경로는 12 m로 제한하며 픽셀 광선은 캐시한다.
6. **15 Hz 요청이 실제 10 Hz로 감소**: 외부 발행 주기와 내부 촬영 주기가 중복
   적용되면서 일부 프레임을 건너뛰었다. 촬영 기한은 한곳에서 누적 관리하고,
   기존 ROS tick마다 전송 대기열을 비운다. 촬영 사이에는 다시 렌더하지 않고,
   긴 공백 후 밀린 프레임을 몰아서 만들지 않는다. 기존 시험에서는 1초에 10회,
   수정 후에는 정확히 15회 촬영·전송되는 회귀 검사를 추가했다.
7. **느린 시뮬레이션에서 정상 FCU가 오래됐다고 판정**: FCU 상태는 시뮬레이션
   시간 약 1초마다 도착하지만 현재 환경에서는 벽시계 약 3.13초가 걸린다.
   시뮬레이션에서는 ROS 수신 시각을, 실물에서는 기존 벽시계를 사용하도록
   구분했다. 시뮬레이션 시계 정지·역행 검사는 계속 별도로 적용한다.
8. **종료된 레코더의 요청이 다음 세션에 남음**: 종료가 확인된 프로세스의 미완료
   요청을 정리하고 이전 세션의 응답이 새 세션을 변경하지 못하게 했다. 대기열에
   들어간 Ping360 설정도 실행 시점에 동일한 세션 잠금을 검사한다.
9. **MAVProxy가 승인된 IMU 주파수를 다시 덮어씀**: 기본 ALL-stream 요청이 벽시계
   15초마다 반복됐다. 기본 실행 인자에 `--streamrate=-1`을 적용해 SR 기본값과
   명시적 메시지 주파수 설정을 유지한다. 사용자가 지정한 MAVProxy 인자는 보존한다.
   시뮬레이션에서는 ATTITUDE 20 Hz만 요청하며 실물의 기존 요청은 유지한다.
10. **AHRS 시각으로 가속도 캐시의 신선도를 판단**: GUI·정책의 시뮬레이션 설정에서
    자세와 원시 각속도·가속도의 입력 및 시각을 분리했다. 모델의 원시 IMU는 이미
    body FLU 축으로 변환되어 있고 `fcu_link`를 사용한다. 원시 IMU가 늦거나 잘못된
    프레임이면 수집·정책 입력을 거절한다. 기본 실물 입력, 23D state, 기존 7개 시각
    열은 유지하고 별도 원시 시각을 행별 감사 기록에 남긴다. 학습 입력의 FCU 시간축
    검사도 맞췄으며, 서로 다른 IMU 입력 계약의 조용한 병합은 내보내기에서 거절한다.

렌더러 실패 시에도 실패한 촬영이 예정된 한 슬롯을 소비하도록 했다. 고장 상태에서
ROS tick마다 100회/초 재시도하던 경로가 설정된 15회/초 이내로 제한됨을 검증했다.

기존 선택 패키지가 항상 설치됐다고 가정하던 GUI 미션 시험과 이미 변경된
핑거 기본값 시험도 수정했다. 미션 UI를 다시 추가하거나 기존 제어 기능을 바꾸지는 않았다.

픽셀 수에 비례하는 계산과 작은 텍스처로 비용을 제한했다.

## 실제 실행 검사

동일 연구 수영장·분산 물리·GUI viewer, 비무장 초기 자세 유지 상태에서 실제 ROS를
구독해 검사했다. 설정값과 실측값을 분리한다. 기존 4 Hz 설정의 12초 측정에서는
RTF 0.352, 두 카메라 실제 source rate 4 Hz, 10 Hz 수집 시점 42개에서 영상 나이
0.30–0.50초, 유효율 0%, 중복 전환 각 25회였다. IMU·수심·DVL은 100% 유효했다.

이 조건에서는 기본 4 Hz를 VLA 수집용으로 사용할 수 없다. 실행 시 사용하는
수집기 기본 영상 freshness 제한은 0.25초다. 벽시계 FPS와 시뮬레이션 시간 Hz는
서로 다른 수치이며, 오래된 영상을 최신 시각으로 다시 찍어 통과시키지 않는다.

카메라 수정 직후 같은 조건에서 8초 DDS 발견 대기 후 12초 동안 다시 측정했다.

| 지표 | 기존 4 Hz | 최종 VLA lite + pool_lite |
|---|---:|---:|
| 카메라 고유 source stamp 기준 주기 | 4 Hz | 두 카메라 각각 15.013 Hz |
| 10 Hz 수집 시점 검사 개수 | 42 | 39 |
| 영상 유효율 | 0% | 두 카메라 모두 100% |
| 영상 source age | 0.30–0.50초 | 0.03–0.06초 |
| 중복/역행 영상 전환 | 각 25회 | 0회 |
| 전체 RTF | 0.352 | 0.320 |

최종 카메라 사이 source stamp 차이는 0초이며, 실제 데이터는 640×360 RGB uint8이다.
IMU·수심·DVL도 검사한 39개 시점에서 모두 유효했다. 다만 IMU 고유 source 주기는
약 8.64 Hz이고 최대 age가 0.2475초로 제한 0.25초에 근접했다. 짧은 정지 검사에서의
100% 유효율이 장시간 조종 중 무결성을 보장하지는 않는다. IMU 중복 stamp 전환은
5회였으며 카메라 중복과 구분했다.

전체 RTF는 오히려 약 9% 낮아졌다. 카메라 촬영량이 4 Hz에서 15 Hz로 늘어난
조건으로, 전체 실행 속도 향상으로 해석하면 안 된다. 두 카메라의 벽시계 수신률은
각각 약 4.75 fps였다. [최종 실제 측정 JSON](../assets/pre-vla-live-inputs-20260914.json).

비무장·초기 자세 유지 상태에서 단일 GUI RC 발행자로 모든 축을 0으로 유지한
`connection_check`를 실제 수집기 시작/종료 서비스로 기록했다. 시뮬레이션 시간
5초에 51행을 저장했고 양쪽 영상 stamp는 각각 51개 모두 고유했다. 상태와 action은
모두 유한하며 네 validity flag가 모두 100%였다. 성공 라벨은 `false`로 유지했고,
검사 후 RC를 해제했으며 기체 위치 변화는 0이었다. LeRobot 변환과 실제 U0 데이터
로더의 inspection 경로를 통과했다. 16-step 전체 chunk는 36개이며, 로더 입력은
video `[1,2,224,224,3]`, state `[1,23]`, action `[16,4]`, packing 후 state `[1,64]`,
action `[16,32]`였다. 최적화나 정책 추론은 실행하지 않았고 이 자료는 작업 시연으로
간주하지 않는다.

브라우저 미리보기를 일시 정지한 별도 6초 구독 검사에서도 두 카메라 source rate는
약 15.05 Hz, 영상 유효율은 100%였다. 표시 속도와 센서 발행 주기가 독립적임을
실제 실행으로 확인한 뒤 미리보기를 기본 4 fps로 복원했다.

### 중단 이후 IMU 수정·재검증

기존 컨테이너가 없는 상태여서 동일한 로컬 이미지로 Humble 실행 환경을 복구했다.
최신 collector/policy 패키지를 다시 설치했고, MAVROS launch/주기 설정 스크립트가
현재 소스를 가리키는 것도 확인했다. 원시 IMU는 50 Hz로 관측됐고, ATTITUDE 20 Hz
요청이 승인된 뒤 실제 AHRS 출력은 약 10 Hz였다. 요청값을 실측값으로 표시하지 않는다.
MAVProxy의 15초 주기를 넘는 30초 관측에서 영상·AHRS·원시 IMU·수심·DVL은 모두
유효했다. 원시 IMU age는 0.02초였으며 AHRS age도 0.25초 제한 안에 들었다.
최종 30초 검사에서 AHRS 최대 age는 0.01초, 영상은 0.06초였고 카메라 중복은 0이었다.
전체 RTF는 **0.203**이었다. 재구성된 X11 viewer/웹 실행 환경의 수치이므로 앞선
0.320과 직접적인 최적화 전후 비교로 사용할 수 없다. 현재도 실시간 실행보다 느리다.
[최신 실제 측정](../assets/pre-vla-live-motion-20260914.json).

새 `connection-check-motion` 자료도 비무장·0입력으로 51행/5초를 기록했고,
별도 원시 IMU stamp 51개가 모두 고유했다. 내보내기가 행별 IMU 감사 기록을 그대로
보존했고 실제 U0 로더에서 완전한 36개 chunk와 기존 입력 shape를 다시 확인했다.
이 재검증에도 ARM·모드 변경·정책 추론·학습은 포함하지 않았다.
[원시 IMU 감사 요약](../assets/pre-vla-motion-audit-20260914.json),
[최종 실제 로더 결과](../assets/pre-vla-loader-20260914.json).

실제 GUI API에서도 세션 준비 → 설정 변경 거절(HTTP 400) → 대기 세션 종료 →
잠금 해제와 수집기 프로세스 종료를 확인했다. 이 검사에서는 ARM·모드 변경·RC 입력이나
episode 시작을 수행하지 않았다. 준비된 context에는 경량 광학 설정 파일 내용이 포함됐다.

로컬 원본·실행 로그·연결 자료는 `outputs/pre-vla-readiness-20260914/`에 보관한다.

## 실행·재현

1. GUI의 환경에서 **Research pool · distributed physics**를 선택한다.
2. **ROS 센서 출력 → VLA lite · 640×360 @ 15Hz**, **광학 → 수중 풀 · 경량 광학**을
   선택하고 적용한다. 미리보기는 기본 4 fps로 둔다.
3. 시뮬레이션을 시작하고 초기 정렬 완료를 기다린다. VLA 창에서 작업 지시문과
   실제 조종 모드를 맞춘다. 세션 준비 후 센서·시계·모드·제어권 조건을 확인한다.
4. 사용자가 ARM 후 시작 위치에서 실제 시연을 녹화한다. 접근→갈퀴 정렬→분리→정지
   한 번이 한 episode이며 성공/실패를 구분해 저장한다. 저장 후 리셋하려면 세션을 종료한다.

ROS 환경에서 구독만 하는 검사:

```bash
source /opt/ros/humble/setup.bash
source rospkg/install/setup.bash
# 실행 중 시뮬레이션과 같은 ROS_DOMAIN_ID, RMW 설정을 사용한다.
.venv/bin/python uuv_mujoco/current/tools/check_vla_live_inputs.py \
  --duration 30 --imu_motion_topic /mavros/imu/data_raw \
  --output outputs/vla-input-check.json
```

ROS 없이 실제 렌더·비용 검사:

```bash
MUJOCO_GL=egl python uuv_mujoco/current/tools/render_camera_validation.py \
  --output_dir outputs/camera-validation --frames 30 --warmup 5
```

현재 워크스테이션에서는 MuJoCo 3.8을 포함한
`/home/khm/robotics/IsaacLab/isaaclab.sh -p` 또는 컨테이너의 `.venv/bin/python`을
사용했다. 새 필수 의존성은 추가하지 않았다. 수집기/정책 시험은 ROS 환경이 필요하다.
기존 Python bytecode가 소스와 불일치한 사례가 있어 회귀 전후 검사에는 서로 다른
`PYTHONPYCACHEPREFIX`를 사용했다.

## 판단의 한계

최종 로컬 검증은 수집기·정책·학습 입력 80개, MAVProxy 설정 2개,
카메라·GUI·ROS launch 76개로 **158개 테스트가 통과**했다. 별도 Node 브라우저
검사 2개, Python 오류 검사와 shell/JS 구문 검사도 통과했다. 신규 결함 회귀 검사는
별도 기준 소스로 실패를 확인한 뒤 수정 소스로 통과시켰다.

실물 질량·배수량·항력·센서 장착 및 광학 계수의 추가 실측, 실제 부표 작업 시연,
학습된 ROV 정책의 폐루프 성공률은 별도 검증이 필요하다. 이 작업에서 접촉 안정성을
위한 0.5 ms 간격이나 20 N 자석 기준을 성능 목적으로 낮추지 않았다. skybox 변경 전후
질량·관성·충돌·관절·자석·초기 상태 배열이 동일함을 확인했다.

검사에 통과한 연결 자료를 task demonstration으로 바꾸어 학습에 넣지 않는다.
