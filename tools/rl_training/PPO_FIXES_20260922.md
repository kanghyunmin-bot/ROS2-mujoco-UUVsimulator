# PPO pipeline corrections — 2026-09-22

## Confirmed defects and changes

1. Feedback names the actual applied action ID. A held action owns rewards up to
   the next command boundary, including waiting for the next VLA result.
   Terminal events cancel the pending unapplied action. Traces retain observation,
   command-start and boundary times. Asynchronous inference latency still exists.
2. Visibility rays match rendered groups 0–2. They pass only through the named
   `front_optical_window` when its alpha is below 0.1 (scene alpha: 0.06), advancing
   through its surfaces. The vehicle body, fork, walls and other obstacles are not
   excluded. An opaque optical window blocks the ray. Multi-point target sampling
   handles partial visibility. This is a geometric proxy, not pixel segmentation.
3. PPO previously discarded all four epochs when the final step exceeded its
   limits. All four saved production batches reproduced that failure. Each epoch
   now retries from its pre-step policy **and Adam moments**, halving the step up
   to six times. Safe earlier epochs survive later rejected steps. Total policy
   KL stays at or below 0.01 and maximum mean residual change at or below 0.005.
   Diagnostics describe the retained policy, not a discarded proposal.
4. Initial evaluation is followed by cycles of training, fresh incumbent
   evaluation, and candidate evaluation. Matching scene resets and VLA inference
   seeds are used; physics timing and sensor noise can still differ. Evaluation
   data is never used for PPO. Unchanged policies skip both comparison rollouts.
   Promotion requires equal counts, no decrease in cumulative fork/hand-or-fork/
   release counts, and either increased counts or mean reward gain >= 0.25.
   This noise margin is a screening rule, not statistical significance. Rejected
   candidates with lower tier counts or reward loss >= 0.25 restore incumbent
   policy and Adam state. Inconclusive comparisons retain the learner and Adam
   state for the next on-policy rollout without replacing the best checkpoint.
   `training-latest.pt` and `accepted.pt` therefore serve different purposes.
   The initial baseline is saved but not counted as a promotion.
5. GUI separates attempted updates, actual weight changes and accepted candidates.
   Historical runs without these fields remain explicitly labelled as attempts.
   Exploration, incumbent evaluation and candidate evaluation have separate plot
   series. Previously all were connected as one apparent growth curve.

Recording success means valid release, retaining the strict tier in metadata.
Interrupted exports keep their failure flags. Previous checkpoints and original
human demonstrations are not modified.

## Infrastructure failure isolation and resume

The production run `20260922-021706-d2e406` stopped after MuJoCo reported
`Physics instability at 453.301500 s` (buoy rope DOF 28). The subsequent
`Waiting failed: simulation tick` was a symptom of the exited simulator.
This change contains that failure; it does not fix the underlying rope dynamics.

- A physics crash, simulation/sensor timeout or exited worker retires that
  environment for the current run. Cleanup runs independently so remaining
  inference requests are not blocked by container shutdown.
- The entire interrupted trajectory is discarded, including earlier transitions.
  It contributes neither PPO samples nor a success/failure episode. Diagnostic
  metadata is retained separately in `infrastructure-failures.json`.
- Three retired environments in one run, no remaining environment for a selected
  model, or an unclassified worker error stops training. There is no restart loop.
- Unequal evaluation counts caused by exclusions prevent promotion and rollback;
  the learner remains available for the next complete comparison.
- Resume chooses the newest compatible `training-latest.pt`, restoring policy,
  critic and Adam state. Reward, timing, base model and other relevant settings
  must match. Incompatible settings retain the prior legacy-seed behavior.
  GUI shows inherited updates separately from updates in the current run.
- Fault injection `rl-discard-verify-20260922-025042`: killed one of two containers
  after three baseline transitions. The other completed all four phases and one
  PPO update; the failed attempt never appeared in episode statistics.
- Eleven focused unit tests passed, including an unequal-evaluation regression
  that fails with the previous rollback behavior. Python compilation passed.
- Second injection `rl-discard-verify-20260922-025301` killed a container during
  the training phase. Three partial transitions were discarded; the saved PPO
  batch contained exactly the surviving episode's 11 transitions. One real
  parameter update and both subsequent evaluation phases completed, exit code 0.
  The retired worker was never relaunched, and all test containers were removed.
- Production resumed as `20260922-025444-1e76ee`, six environments, 60 s per
  attempt, existing 100-cycle configuration. The first collection checkpoint
  matches the prior run's saved policy (including critic) and Adam state exactly;
  two inherited updates are preserved. The updated GUI is served at `/rl`.
